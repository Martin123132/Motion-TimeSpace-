# Private Fork Heuristics for Martin-Style Search

Private navigation note. This is not a theorem, axiom, claim, or public-facing statement. It is a search discipline for future MTS derivation work.

## Time-Flow Fork Rule

Do not reject a branch merely because its explanatory language appears to reverse the usual story of GR/SR time dilation.

The branch is still allowed to be investigated if it might preserve the measured operational facts:

- local clocks match SR/GR tests in the tested regimes;
- null propagation still reproduces light-cone structure and Maxwell limits;
- massive bodies still recover Newtonian mechanics and GR where GR is measured;
- conservation, covariance, and stress-energy bookkeeping remain intact;
- any new interpretation produces extra testable structure rather than just rewording standard results.

## Working Intuition

Space and time are not treated as two separable things in the search logic. Traversing space is also traversing time/spacetime, so when a fork says "local time slows" or "motion through TIME increases", translate it into operational questions before judging it.

Useful translation questions:

- Is this a statement about proper time along a worldline, coordinate time, phase time, action accumulation, or an emergent clock variable?
- Does the branch reproduce the invariant interval and the known clock-rate experiments?
- Does "photon timelessness" follow from null worldlines/no rest frame, or from a distinct MTS mechanism?
- Can gravity be read as the local "climbing gear" that changes how a system traverses the global spacetime/motion-time-space structure?
- Does the route help derive coupling, Newton's constant appearance, Maxwell/EM stress, or local GR recovery?

## Kill Conditions

The heuristic does not protect a branch if it:

- breaks tested SR/GR clock predictions without a compensating observable derivation;
- violates local Lorentz tests, WEP bounds, PPN limits, or energy-momentum conservation;
- only changes words while adding no derivable equations or testable distinction;
- requires an unsourced closure parameter where the project needs a parent derivation.

## Use In Future Checkpoints

When a derivation fork appears to clash with standard time-dilation interpretation, the next checkpoint should classify the clash as one of:

```text
same observables, different interpretation;
different observables, testable correction;
coordinate-language confusion;
hard contradiction with experiment;
unresolved but potentially derivable coupling route.
```

Only the last two require serious danger flags. The first two are worth pursuing if they improve derivability or source coupling.

## Opposite-Looking Time-Dilation Branches

If a branch appears to work structurally but its explanatory language seems opposite to GR time-dilation language, do not demote it on wording alone. First perform an observable-map audit:

- identify which time variable is being used: proper time, coordinate time, phase/action time, memory/source time, or background traversal/process time;
- check whether the tested clock observable still matches SR/GR in the local limit;
- check whether the apparent reversal is only a dual variable, reciprocal rate, or public/private readout swap;
- check whether the branch gives a derivable coupling, EM/Poynting/Hodge-flow route, or Newton/GR reduction advantage;
- demote only after the observable map fails, not before the map is written.

This is not permission to contradict clock experiments. It is permission to investigate a fork before declaring it dead.
